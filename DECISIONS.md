## 2026-07-24

### Phase 0 & 1 review (before starting Phase 2)

Checked the existing skeleton against the PRD's acceptance criteria before building on top of it. Found solid:
- Real Google OAuth sign-in already working end-to-end (Auth.js / NextAuth v5 beta)
- Supabase schema from PRD §8 (`users`, `preferences`, `oauth_tokens`, `briefings`, `commands_log`, `allowlist`) already provisioned in the "Daily Brief Web" Supabase project
- Nav shell has exactly 3 sections (Today / History / Settings); Today and History share one `BriefingFeed` component
- Command box correctly scoped to the Today page only
- Onboarding wizard (6 steps + progress bar) working against local/mock state (`localStorage`), matching Phase 1's intended scope

Bug found and fixed: `@supabase/supabase-js` was present in `node_modules` but never recorded in `package.json`/`package-lock.json` — a clean `npm install` or a Netlify build would have failed as soon as any code imported it. Installed properly via `npm install @supabase/supabase-js`.

### Microsoft/Entra ID sign-in dropped

**Decision:** Removed Microsoft as a sign-in option. Google is now the only supported provider.

**Why:** Couldn't get a working Microsoft Entra ID app registration set up (blocked in the Azure Portal). Rather than block Phase 2 on that, cut it.

**What changed:**
- `auth.ts` — removed the `MicrosoftEntraID` provider; `AuthProviderId` type narrowed to `"google"`
- Supabase migration `0003_google_only_provider` — narrowed the `provider` CHECK constraint on `users` and `oauth_tokens` to `'google'` only
- Sign-in UI, Settings page, README, `.env.local(.example)` updated to match

**Kept flexible on purpose:** the `provider` column/type wasn't deleted, just restricted — re-adding a provider later (Microsoft or otherwise) is additive, not a schema rewrite, if the Entra ID issue ever gets resolved.

### Phase 2: backend integration implemented

- **Allowlist-gated sign-in** — `auth.ts`'s `signIn` callback checks the Supabase `allowlist` table by email (case-insensitive) before allowing sign-in to complete; denied users land back on the sign-in screen with a real "you're not on the allowlist" message instead of Auth.js's default error page
- **OAuth refresh tokens encrypted at rest** — AES-256-GCM (`app/lib/crypto/token-cipher.ts`), keyed by `TOKEN_ENCRYPTION_KEY`, stored in `oauth_tokens.encrypted_refresh_token`
- **`access_type=offline` + `prompt=consent`** on the Google provider so a refresh token is issued on every sign-in, not just the first — needed since the scheduled briefing job (Phase 3+) has to read Calendar without the user present
- **User/session wiring** — a `users` + `preferences` row is created for every new signed-in email (upsert on email, in the `jwt` callback); the resulting `users.id` is attached to the session as `daybreakUserId` so server code never has to re-look-up "who is this" by email
- **Onboarding now writes through to Supabase** — each wizard step (schedule/topics/location/notify/done) calls a Server Action (`app/lib/onboarding/actions.ts`) that updates the real DB row, in addition to the existing local state. The wizard's own UI still *reads* from `localStorage` (Phase 1's design, untouched) — Supabase is the durable store other phases will read from, not yet the wizard's read path. A failed save now shows an inline error and keeps the user on the step, instead of silently advancing
- Generated Supabase TypeScript types (`app/lib/supabase/database.types.ts`) so all of the above is fully typed against the actual schema

**Not done as part of Phase 2:** allowlist management UI (still direct SQL edits) — PRD §6.3 lists it as a nice-to-have, and the Phase 2 roadmap entry only calls for the sign-in check itself.

### Public-launch scope decision: dropped Gmail, narrowed Calendar to read-only

The original ask was "make this a public app that I ship to users," which is a real pivot from the PRD's framing ("private/allowlisted access... not for public release"). Researched what "public" actually requires before touching code:

- Google classifies OAuth scopes as non-sensitive / sensitive / restricted. **`gmail.readonly` is a restricted scope** — going public with it requires Google's CASA (Cloud Application Security Assessment), a paid third-party security audit (roughly hundreds to a few thousand dollars depending on tier) that must be **redone every 12 months**, on top of brand verification, a demo video, and a privacy policy. The review "can potentially take several weeks."
- Calendar *write* access (`calendar.events`) also appears to fall in the restricted tier. Calendar *read-only* access (`calendar.events.readonly`) is only "sensitive" — real verification required, but no CASA audit.

**Decision (user call):** reading a user's email to find meetings was judged too intrusive regardless — drop Gmail entirely, not just to dodge CASA. Calendar is kept, but read-only: "just to see if there are any meetings scheduled."

**What changed:** `auth.ts`'s `GOOGLE_SCOPES` is now `openid email profile calendar.events.readonly` — no Gmail scope at all, and Calendar is read-only instead of read/write.

**Downstream consequence for PRD §7.3 (typed commands) — not yet built, but scoped differently now than the PRD describes:** with no Gmail scope and read-only Calendar, the typed-command pipeline can *surface* calendar info (e.g. "what's on my calendar today") but **cannot** do any of the PRD's write-side command list — create/reschedule/delete calendar events, draft or send email. Those would need `calendar.events` (write) and/or Gmail scopes back, which reopens the CASA question. Revisit this explicitly when Phase 5 starts, rather than assuming the original PRD command list still applies.

**Still open, not yet done, for an actual public launch:**
- [ ] Google OAuth verification for `calendar.events.readonly` (sensitive-tier — brand verification + demo video + privacy policy; no CASA needed at this scope)
- [ ] A real public signup flow — allowlist is still opt-in/manual (direct SQL) today, blocking every non-approved email
- [ ] Terms of Service + Privacy Policy pages (required for verification anyway)
- [ ] Free-tier limits that won't survive real traffic: market-data API (Alpha Vantage/Finnhub), Resend (email sending) — both need paid-tier review before public usage
- [ ] Cost monitoring / budget alerts on the Claude API — PRD §9 already calls for this, becomes load-bearing (not optional) once user count isn't fixed

## 2026-07-25

### Phase 3: briefing generation pipeline implemented

Built the PRD 7.2 pipeline as a manually-invokable route rather than a cron-wired one — Phase 4 owns the "who's due now" batch query and the GitHub Actions cron trigger; this phase is just the generation logic itself, callable per-user, per the roadmap's own split ("Test by manually invoking the route before wiring up cron").

**New modules:** `app/lib/briefing/outfit.ts` (rule engine), `app/lib/briefing/sources/{weather,market,news,calendar}.ts` (one per data source), `app/lib/briefing/generate.ts` (orchestrator — fans the four sources out via `Promise.allSettled`, each independently degrading to `null` per PRD 7.2's degraded-state rule, then upserts into `briefings` keyed on the table's existing `unique (user_id, date)` constraint). `app/api/briefing/generate/route.ts` is a `POST`, session-gated the same way Server Actions already are (`getCurrentUserId()`) — generates *the signed-in user's own* briefing. No UI trigger was added; invoke it from the browser console while signed in: `fetch("/api/briefing/generate", {method:"POST"}).then(r=>r.json()).then(console.log)`. Today/History still read from `lib/mock-briefings.ts` — wiring them to real data is explicitly Phase 4's job, not this one's.

**No email summary — not a placeholder, a permanent PRD deviation.** `email_summary_text` is always written as `null`; Gmail access was dropped entirely in the 2026-07-24 public-launch scope decision (see above), so there's no data source for this column anymore. `EmailSection` in the UI still shows the generic "unavailable" message, which is accurate but slightly undersells that this isn't coming back — worth a copy tweak whenever Settings/UI polish (Phase 6) is in scope.

**Data sources and why each was picked:**
- **Weather:** Open-Meteo, no API key (already free per PRD). Two calls — geocode `users.home_location` (free text) to lat/lon, then the forecast endpoint for today's high/low/condition/precip/wind, all in the user's stored `timezone`.
- **Outfit:** a real rule engine (temp band + precipitation + wind, per PRD 7.2), with `preferences.cold_tolerance` shifting the effective temp band by ±5°F and `style_preference` lightly flavoring the garment word — both columns existed since Phase 2 onboarding but were unused until now.
- **Market:** PRD says "Alpha Vantage or Finnhub, swappable." Went with **Finnhub** (`FINNHUB_API_KEY`, free tier) for equities/ETFs, plus **CoinGecko** (free, no key) for crypto, since Finnhub's free tier doesn't do crypto cleanly and CoinGecko does it well with zero setup. The mock's `indices` vs `watchlist` split doesn't map onto anything in the data model (`preferences.market_tickers` is one flat list) — resolved by always fetching SPY/QQQ as fixed "indices" proxies (labeled "S&P 500"/"Nasdaq," same as the mock) since there's no free-tier way to fetch the raw index tickers, and treating the user's actual `market_tickers` selections as the "watchlist." Confirmed working end-to-end for crypto without any key.
- **News:** Google News RSS (`rss-parser` dependency, no key) per topic is the primary source, exactly per PRD. Guardian API is genuinely optional — only called when `GUARDIAN_API_KEY` is set, so the pipeline is fully testable without anyone going and getting a Guardian key. Pooled candidate headlines get condensed to 1 (occasionally 2) per topic by Claude, using **structured JSON output** (`output_config.format`, not prefill/tool-use hacks) so the result is guaranteed to match the `NewsHeadline[]` shape the UI already expects.
- **Calendar:** first phase to actually consume the `oauth_tokens.encrypted_refresh_token` stored since Phase 2. Talks to the Calendar v3 REST API directly with plain `fetch` (refresh-token exchange + `events.list`) rather than pulling in the `googleapis` package — not worth the dependency for one read-only call.

**Claude model: defaulted to `claude-opus-5` for the news-condensing call**, per current house policy (skill-mandated default, "never downgrade for cost — that's the user's decision, not yours"). Flagging explicitly because this project has its own, earlier, deliberate cost-consciousness (PRD 9's "hard daily generation cap... monthly budget alert on the Claude API," see also the public-launch checklist above listing "Cost monitoring / budget alerts on the Claude API" as still-open) — this is a small, cheap-per-call task (condense ~10-20 headlines into ~6), so `claude-haiku-4-5` is a very plausible swap once this runs daily for more than a couple of users. It's a one-line constant (`CLAUDE_MODEL` in `app/lib/briefing/sources/news.ts`) specifically so that decision is easy to make later without touching anything else.

**Bug found and fixed:** Open-Meteo's geocoding endpoint does fuzzy *name* matching, not free-text search — querying it with `"Cerritos, CA"` (the exact format onboarding's own placeholder text asks for, `app/onboarding/location/page.tsx`) returns zero results, while `"Cerritos"` alone matches. `geocodeLocation` now strips to the part before the first comma before querying. This would have silently null'd out weather (and therefore outfit) for a large fraction of real users, since most people type a location the way the placeholder suggests.

**Known issue found, not fixed — Calendar decrypts to an auth-tag failure.** Manually running `generateBriefing` against the builder's own account (`adrianwong055@gmail.com`, a real signed-in session from earlier today) fails to decrypt `oauth_tokens.encrypted_refresh_token` — `decryptToken` throws "Unsupported state or unable to authenticate data" (an AES-256-GCM auth-tag mismatch, i.e. wrong key). The token itself is fresh (`connected_at` from today), so this isn't stale data from the Phase 2 merge conflict — most likely `TOKEN_ENCRYPTION_KEY` differs between wherever that sign-in actually happened (e.g. a deployed Netlify instance's dashboard-configured env vars) and the local `.env.local` used for this test. The pipeline handled it correctly either way — Calendar degraded to `null` rather than crashing the rest of the briefing — but the underlying key mismatch is real and needs the user to sort out (likely: confirm local `.env.local` and Netlify's `TOKEN_ENCRYPTION_KEY` actually match, then sign out/in once against whichever environment will run cron in Phase 4 to get a token re-encrypted under the right key).

**Verification performed:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean. Ran `generateBriefing()` directly (not through the HTTP route — no way to complete Google's OAuth consent screen non-interactively) against the one real allowlisted account, live, twice (before and after the geocoding fix). Confirmed live: Open-Meteo weather + the outfit rule engine, CoinGecko crypto pricing. Confirmed graceful degradation (not a crash) for: Finnhub equities/indices and Claude news (no API keys configured yet — expected), and Calendar (the key-mismatch issue above). The HTTP route itself (`getCurrentUserId()` → 401 gating, `NextResponse.json` wrapping) was not separately exercised — it's a thin, pattern-matched wrapper around the same `generateBriefing()` call every onboarding Server Action already uses.

**Still open for Phase 4:** the "who's due now" query + GitHub Actions cron entry point, the notification email, and connecting real `briefings` rows to Today/History (still mock-data-backed). Also worth deciding then whether the Claude model for news should move off Opus.

### Full visual redesign against the "Modernist" design handoff

User supplied a high-fidelity wireframe (`design_handoff_daybreak_app/` — `Daybreak.dc.html`, `modernist-styles.css`, `README.md`): flat black/white/red design system, zero border radius, Archivo font, 2px section dividers. Treated as a full replacement of the app's visual layer (previous Tailwind-default look + dark mode, which the handoff doesn't define — dark mode was dropped rather than invented) and a restructuring of navigation and several screens. This is the single largest change to the app so far — touches nearly every route.

**Two things in the design conflicted with earlier deliberate decisions — asked before building, didn't guess:**
1. **Gmail copy.** The design's onboarding/Settings copy says "Gmail + Calendar" and the Day Detail modal has an Email-summary section, but Gmail was dropped entirely on 2026-07-24 (see above). User chose: keep Calendar-only, fix the copy. Done — every "Gmail" mention now reads "Calendar" only, and Day Detail has no Email section (Weather/News/Calendar only).
2. **Command bar.** The design's Today page leads with a full typed-command + confirm-card flow, whose own demo example reschedules a calendar event — a *write* action the app deliberately can't do (Calendar is `calendar.events.readonly`, same CASA reasoning as Gmail). It's also Phase 5 work, not built yet (the prior placeholder was explicitly "non-interactive... no parsing logic belongs here yet"). User chose: build the real visual (input + send button, matching the design), but submitting shows an honest "not available yet" note instead of a fake confirm card with invented data — no functionality that isn't real. `app/(shell)/today/command-bar.tsx`.

**Navigation restructured:** 3 tabs (Today/History/Settings) → 2 tabs (Today/Calendar) + a profile menu (avatar initials, name, chevron → Settings/Sign out dropdown) as the *only* path to Settings — no direct Settings tab, per the design. Went with the design's default top-bar layout only, not the alternate sidebar layout it also specifies as a config toggle — building and maintaining two full nav layouts for a personal project wasn't worth it; easy to revisit if wanted. Mobile got no separate treatment either (the design doesn't specify one — "a config toggle, not a responsive breakpoint"), so the old bottom-tab-bar mobile nav is gone; the same top bar now renders at all widths.

**History → Calendar: from a 5-day date-picker to a real month grid.** The old `/history` page (and its mock-data date picker) only ever supported a narrow rolling window relative to "today" — structurally incompatible with "browse any month back to Jan 2026," which the redesign requires. Rather than extend throwaway mock code, wired Calendar directly to real Supabase `briefings` data: `app/lib/briefing/read.ts` adds `getBriefingDatesInRange` (which days in a visible month have a briefing + pinned status) and `getAdjacentBriefingDate` (nearest earlier/later date with a briefing, for the Day Detail modal's Prev/Next — can cross a month boundary the grid hasn't loaded, so it's a real query, not client-side array math). `Today` was wired the same way (`getBriefingForDate`) rather than leaving it mock-backed while Calendar went real — having one page real and the sibling page mock would've been a stranger inconsistency than just finishing the wiring `[[daybreak-web-context]]` had flagged as Phase 4's job. Phase 4's remaining scope (cron, "who's due now" batch query, notification email) is untouched by this.

**Day Detail is a modal, not a page** — clicking a day with a briefing opens an overlay via client state (not a URL/route change, matching the design's explicit "no page navigation occurs"), fetching that one day's data on demand from a new `GET /api/briefing/[date]` route rather than the Calendar page preloading every day's full briefing up front. That route also resolves Prev/Next-day navigation server-side (chevrons + Left/Right arrow keys, added in a small follow-up to the original wireframe upload) since "nearest date with a briefing" needs a real query, not just paging through whatever's in the currently-rendered month.

**Data shapes changed to match the design, not just its styling:**
- **Weather** gained `windSpeedMph`/`windDirection` (Open-Meteo's `wind_direction_10m_dominant`, converted to a 16-point compass label) — the design's weather line shows wind.
- **Markets** dropped the indices/watchlist split entirely — the design is one flat table (Symbol/Name/Price/Change) with no separate "index" row, mapping directly onto `preferences.market_tickers`. Also added a `name` field (static lookup for the known catalog — "Apple," "Bitcoin," etc. — falling back to the bare symbol for anything free-typed beyond it, since tickers are no longer restricted to a fixed list).
- **News** gained a `summary` field (1-2 sentences) and a real `publishedAt` timestamp (for "2h ago"). The summary is Claude-written but explicitly constrained to *never* add specifics beyond the candidate headline (and Guardian's `trailText` when that source is configured) — with only a bare RSS title as input, asking for a longer summary without that constraint risked the model inventing plausible-sounding details that aren't real reporting. `sourceIndex` in the structured-output schema maps each written headline back to its original RSS/Guardian candidate so the timestamp is the real one, not fabricated.
- **Calendar events** swapped `location` for `meta` (a computed "30 min · Conf Room B" — duration derived from `start`/`end`, plus location when present), matching the design's row format more closely than a bare location string did.
- Topic and ticker catalogs (`app/lib/preferences/types.ts`) expanded to match the design's suggestion lists (added Markets/Climate/Politics/Education/Travel; AMZN/TSLA/META/DIS/ETH-USD) — additive only, existing saved values still valid since these were never enum-enforced at the DB level.
- Kept `OUTFIT_STYLE_OPTIONS`'s 4th option ("Formal") even though the design's onboarding mock only shows 3 — dropping it would've orphaned anyone who'd already picked it, and the design gives no indication removing it was deliberate rather than just an abbreviated mock.

**Settings/onboarding editing pattern — one deliberate split.** Schedule, home location, and notification email stay read-only-with-an-"Edit"-link (jumps to the matching onboarding step via the existing `?from=settings` pattern, unchanged) — the design's own prototype leaves these fields genuinely non-interactive (no `onChange` wired anywhere in the source, not just visually static), so there's no alternative in-place-editing behavior to match. Topics and tickers are the one section that *is* wired live in the prototype (real `addTopic`/`removeTopic` state), so those now save immediately on every add/remove (`saveTopicsStep`, reused from onboarding) rather than routing through a step page — a real UX split, not an oversight.

**New backend, not just new screens** (the design specs these directly; PRD/DECISIONS had them as unscoped nice-to-haves):
- **Allowlist management** in Settings — real add/remove against the `allowlist` table (`app/lib/settings/actions.ts`), replacing direct-SQL-only editing.
- **Google "Disconnect"** — deletes the stored `oauth_tokens` row. Deliberately does *not* sign the user out (Google is also the sign-in provider; losing both at once would strand them) — Calendar just degrades to null afterward, same as any other missing-token case. Signing in again re-grants and re-stores a fresh token.
- **"Preview onboarding flow"** in Settings — built as a fully self-contained, non-persisting walkthrough (`app/(shell)/settings/onboarding-preview.tsx`) using static demo copy and local-only `useState`, not a "don't-save" flag threaded through the real wizard. The real onboarding step pages already write through to Supabase on every step; a "preview" that could accidentally persist against the signed-in user's real account was worth avoiding entirely rather than trusting a flag not to leak into a Server Action call somewhere.
- Added a "Back" button to every real onboarding step (`getPrevStepHref` in `app/onboarding/steps.ts`) — the design shows one on every step; the app had none before.

**Retired:** `app/lib/mock-briefings.ts` (superseded by `app/lib/briefing/types.ts` now that Today/Calendar read real data), `app/components/feed/` (the old section components, replaced by page-specific rendering since Today's and Day Detail's actual information density differ), `app/components/button-styles.ts` (replaced by the new `.btn`/`.input` CSS classes), the old `/history` route.

**Bug found via testing, not inspection: stale stored data from the earlier Phase 3 test run didn't match the new shapes.** Re-running the read helpers against the one real `briefings` row (generated hours earlier, before today's market/weather shape changes) surfaced `market_json` still shaped as the old `{indices, watchlist}` object rather than the new flat array — which would have thrown at render time (`.map` on a non-array) the moment Today or Day Detail tried to render that row, despite TypeScript believing it was safe (the Json→typed cast can't catch a shape that's stale at *runtime*, only at compile time). Fixed for now by regenerating that one row against the current pipeline. **This isn't a one-off**: there's no data migration step in this project, so any other previously-generated `briefings` rows (from earlier manual testing) will have the same problem until regenerated. Didn't add defensive runtime shape-guards for this — going forward every row is written by the current pipeline in the current shape, so it's a one-time artifact of testing during this build, not an ongoing risk; worth remembering if this comes up again after a *future* shape change.

**Verification performed:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean. Visually confirmed live in-browser (screenshots): sign-in screen, all 5 onboarding step screens including the schedule/location/notify field styling, and the topic/ticker chip picker's full interaction set (open popover, click-to-add a suggestion, remove via ×, free-text "Press Enter to add" for anything outside the catalog) — all working, all matching the design. Re-verified the new `app/lib/briefing/read.ts` query helpers directly against the real account (same non-HTTP technique as the Phase 3 verification) after the stale-data fix above; all returned correctly-shaped data. **Not visually verified live: Today, Calendar (grid + Day Detail modal + Prev/Next-day nav), Settings (allowlist CRUD, account connection/disconnect, onboarding preview), and the nav shell's profile menu** — all of these require a real signed-in session, and completing Google's OAuth consent screen isn't something to do on the user's behalf. Confident in these from code review + the fact that they share the exact same verified CSS/component system as the screens above, but the user should take a first look before treating this as fully done.

### Phase 4: scheduling + delivery implemented

Built the remaining Phase 4 scope per PRD 7.2/10 — the "who's due now" batch query, the GitHub Actions cron trigger, and the notification email. **Today/Calendar were already reading real `briefings` data as of the previous session's redesign pass** (see 2026-07-25 (later) above) — that part of Phase 4's roadmap entry was already done as a side effect of the redesign, not new work here.

**"Who's due now" (`app/lib/briefing/due.ts`, `getDueUsers()`):** deliberately a "their scheduled time has passed in their own local timezone, and they don't have a briefing for local 'today' yet" check, not a tight 15-minute window match. Reasoning: GitHub Actions cron timing isn't guaranteed to the minute (documented to be delayed under load), and a window-match approach would need the cron's UTC firing time to land on the same 15-minute grid as each user's local offset to work correctly. A plain "time has passed + not yet generated" check sidesteps both problems — it's self-healing (a skipped or delayed tick just catches overdue users on the next one) and the actual one-per-day guarantee comes from the "not yet generated" half, backed by `briefings`' existing `unique (user_id, date)` constraint, not from the timing precision of the check itself. Only users with `onboarding_completed_at` set are considered, so nobody gets swept up by the `briefing_time_weekday` column's `'07:00'` default before they've actually finished onboarding. Weekend/weekday time selection is computed per-user in their own timezone (a user's "weekend" can start before or after the server's UTC weekend does); `briefing_time_weekend` falls back to `briefing_time_weekday` when null, matching that field's optional status from onboarding.

**Notification email (`app/lib/briefing/email.ts`, `sendBriefingReadyEmail()`):** used **Resend** — already named as the assumed choice in the previous session's public-launch checklist, and fits the PRD's own "favor well-documented, mainstream libraries" guidance. Sends exactly what PRD 7.2/9 specify: "Your morning briefing is ready ☀️", a link to `/today`, no briefing content in the body. ### Full frontend redesign: Inter, a warm accent system, and light/dark mode

**User's ask:** redesign the frontend with an industry-standard font and modern/clean colors, and add light/dark mode. Open-ended — no specific direction given beyond "modern, clean" — so this session made and documents the actual creative calls rather than asking, same as every other design judgment call this build has made (font pairing, spacing, etc.).

**Font: Archivo → Inter, everywhere, one family.** Inter is the closest thing the 2020s tech industry has to a default UI typeface (Linear, Vercel, Notion, Stripe Dashboard all use it or a near-identical grotesk) — the safest, most defensible "industry standard" call for "modern and clean." Went with a single family for both headings and body (weight-differentiated only) rather than a heading/body pairing — also very common in the same reference apps, and lower-risk than introducing a second typeface's proportions to tune. Mechanically this was a near-zero-touch change: `app/layout.tsx` swaps the `next/font/google` import and CSS variable name, and because every page already consumes fonts through `var(--font-heading)`/`var(--font-body)` (never a hardcoded family), the swap propagated app-wide without editing a single page file.

**Colors: black/white/red "Modernist" → a warm amber "sunrise" accent + neutral grays, with light and dark variants.** Amber/orange is a deliberate callback to the product's own name ("Daybreak") rather than an arbitrary pick — sunrise-toned accents are also a recognizable, current pattern in productivity/morning-routine apps. Dropped the red accent entirely from that role; red is now reserved for a **new, separate `--color-danger` token** (see below).

**Architecture: only ~8 true color primitives are hand-authored per theme; everything else derives via `color-mix()`.** `--color-bg`, `--color-text`, `--color-accent` (+600/700 shades), `--color-danger` (+700 shade) are the only values actually written twice (once for light, once for dark). The entire neutral ramp (`--color-neutral-100`…`900`), `--color-surface`, `--color-divider`, and the tinted `--color-accent-100`/`800` / `--color-danger-100` backgrounds are all formulas like `color-mix(in srgb, var(--color-text) 12%, var(--color-bg))` — they automatically invert direction between light and dark (neutral-100 = "near background," neutral-900 = "near text," in *either* theme) without a second full palette to maintain by hand. This is the same `color-mix()` idiom the codebase already used for muted text everywhere; this redesign just pushed it further up the token stack. **Two things were deliberately NOT derived this way** because a shadow or a modal backdrop shouldn't literally invert to a light color in dark mode: `--shadow-*` are fixed black-based values in both themes, and `.dialog-backdrop`'s scrim is a fixed `color-mix(#000000, transparent)`, not derived from `--color-text`.

**Fixed a real semantic bug in the old system while doing this, not a new one:** the old palette used one accent color (`--color-accent-700`) for *both* decorative kicker text (e.g. "Preferences," "Full schedule") *and* genuine error/negative-value text (form validation errors, "Couldn't save," negative market-change color) — meaning every error message would have silently rendered in the new brand amber instead of reading as an error. Grepped every `--color-accent-700` usage (~18 call sites across 12 files), categorized each as decorative-vs-error by reading its actual context, and repointed the ~9 genuine error/negative-value usages to the new `--color-danger` token, leaving the ~9 decorative kicker usages on the accent. `app/(shell)/today/page.tsx`'s `changeColor()` (negative market change) is included in the error-category group — conventionally red in finance UI, not brand-colored.

**Border radius & elevation:** introduced real rounding (`--radius-sm: 6px`, `--radius-md: 10px`, `--radius-lg: 18px`) replacing the old all-zero "Modernist" radii — soft rounded corners on cards/buttons/inputs/dialogs/tags is close to universal in current "clean SaaS" design, and sharp corners specifically was the previous design's own deliberate brief, not a constraint carried over from this request. Also added a `.dialog` border (subtle divider-colored outline) since dark-mode surfaces read flatter without one.

**Removed:** the entire unused `--color-accent-2*` scale and `.tag-accent-2` class — grepped first to confirm zero real usages anywhere outside `globals.css` itself (dead code from the original design handoff that was ported over but never actually consumed).

**Dark mode mechanics (`app/components/theme-toggle.tsx`, `app/layout.tsx`):**
- Theme resolution order: explicit `data-theme` attribute on `<html>` (user's own choice, persisted in `localStorage`) → `prefers-color-scheme: dark` media query (system default) → light (fallback). CSS encodes this as `:root` (light defaults) → `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {...} }` → `:root[data-theme="dark"] {...}`, so an explicit choice always wins over system preference in either direction.
- **FOUC prevention**: a `beforeInteractive` `next/script` in the root layout reads `localStorage.theme` and sets `data-theme` on `<html>` before hydration — the standard technique every dark-mode library (`next-themes` included) uses. A **raw** `<script>` tag (not `next/script`) was tried first and logged "scripts inside React components are never executed when rendering on the client" in the console — `next/script` with `strategy="beforeInteractive"` is Next's actual supported mechanism for exactly this ("load the script before any Next.js code and before any page hydration occurs," per `node_modules/next/dist/docs/01-app/02-guides/scripts.md`) and was the correct fix.
- **The toggle component itself** (`ThemeToggle`) hit this session's now-familiar `react-hooks/set-state-in-effect` lint rule on the obvious `useState` + `useEffect`-on-mount implementation — the rule flags *any* direct `setState` call inside an effect body, even a legitimate one-time "read a browser-only API unavailable during SSR" read. Rewrote using `useSyncExternalStore` instead: `getServerSnapshot` returns a fixed default so server and initial client hydration render identically (no mismatch), then React automatically re-invokes `getSnapshot` right after hydration to pick up the real value — no `useEffect`/`setState` needed at all. `subscribe()` isn't a real external store (there's no independent data source pushing changes) — it's a custom `window` event `toggle()` dispatches on itself, plus the `matchMedia` "change" listener for live system-preference changes while the tab is open.
- **A known, accepted, dev-only console artifact, confirmed and not chased further:** in `next dev`, the same theme-init script + the intentional `data-theme` mismatch (server has no access to the client's `localStorage`, so it can't render the attribute) produce a React hydration-mismatch warning and (occasionally) a stray "script tag" warning, both wrapped in Next's dev-only `HotReload`/`AppDevOverlayErrorBoundary` instrumentation. `suppressHydrationWarning` on `<html>` does **not** silence this — that prop only suppresses *text content* mismatches, not *attribute* mismatches, a common React gotcha. Verified via a real `npm run build && npm run start` in a genuinely fresh browser tab (a reused tab kept replaying buffered console history from the dev server, which briefly looked like the warnings persisted in production — they don't) that **zero console messages** appear against the actual production build. This exact warning is a widely-documented, accepted trade-off of the "blocking script sets `<html>` attributes before hydration" technique (the same one `next-themes` itself uses and produces), not a real bug — noted here explicitly so it isn't mistaken for unfinished work later.

### Correction to the entry above: `netlify env:get` was returning a masked placeholder, not the real key — the "sync" was based on bad data

**What happened:** while building the Calendar Refresh button (next entry), re-testing locally threw a *new*, more specific error — `TOKEN_ENCRYPTION_KEY must decode to 32 bytes` — not the auth-tag mismatch from before.
